# personal-ai-kb · 个人 AI 知识库

一套**零代码、纯文件**的个人知识库方案：一个文件夹 + Markdown + 一份 AI 操作手册（`AGENTS.md`），借助 AI 编程助手（Kimi Code / Claude Code / Codex 等）完成知识的**入库 → 索引 → 问答 → 总结**闭环。

不带任何个人数据，clone 即可用；换电脑、换新环境，按本文档几分钟就能重建一套。

## 为什么是这个形态

- **AI Native**：核心价值由 AI 提供 -- 你丢一个链接，AI 自动读取、总结、打标签、更新索引；没有 AI，它就是一堆空文件夹。
- **编译 > 检索**：不做收藏夹。每条资料入库时被「编译」成带判断的笔记和项目页，取用时先查索引，不翻原文。
- **零代码、零依赖**：没有数据库、没有向量检索、没有 UI、没有定时任务。处理逻辑就是 `AGENTS.md` 里的提示词流程，改流程 = 改文档。

## 快速开始

1. **克隆本仓库**到你的 AI 编程助手工作目录。
2. **用 AI 助手打开本目录**（`AGENTS.md` 会被自动加载，入库/问答规则即刻生效）。
3. **入库第一条**：对 AI 说 `知识库入库：<任意链接或一段文字>`。链接读取方式按你的环境适配（见下文「输入源适配」）。
4. **直接提问**：如「XX 项目现在有哪些风险项」「帮我整理这周工作总结」-- AI 会先查 `kb/index.md` 再读笔记回答。

```
│   ├── 02-架构文档.md   # 进 / 存 / 取 三问：模板 + 示例 + 架构图
│   ├── 03-技术文档.md   # 技术选型：四原则 + 最简清单 + 决策记录
│   └── assets/         # 架构图（png + html 源文件，可改）
└── kb/                 # 知识库本体（空架子，开箱即用）
    ├── raw/            # 原料层：原文，只读不改
    ├── notes/          # 加工层：单源笔记 + 想法笔记
    ├── projects/       # 加工层：项目页（多对一综合）
    ├── inbox/          # 待处理输入暂存
    ├── index.md        # 目录层：关键词 / 标签 / 项目 → 笔记 的映射索引
    └── tags.md         # 标签系统
```

## 输入源适配（唯一需要你按环境决定的事）

入库流程第一步是「读取链接原文」，按你的环境三选一（在 `AGENTS.md` 第 1 步里改一行即可）：

- **内部文档平台**（如企业 wiki）：配置对应的官方读取工具 / CLI / skill；
- **公开网页**：让 AI 用 web fetch 类工具直接抓取；
- **兜底**：手动复制全文，对 AI 说 `知识库入库：<粘贴的内容>`，永远可用。

## 使用方式速查

| 你想做什么 | 对 AI 说 |
| --- | --- |
| 入库一条链接 / 想法 | `知识库入库：<链接或文字>` |
| 问答 | 直接问，如「XX 项目有哪些风险项」 |
| 项目总结 | `XX 项目总结` |
| 阶段工作总结 | `帮我整理这周工作总结` |

入库过程中 AI 会停下来和你确认两件事：**建议标签**（防标签膨胀）和**新项目页归属**（防项目分裂）。确认后继续，这是设计的一部分，不是卡住了。

## 方法论出处

- 产品：**一页纸 MVP 六格子**（用户 / 问题 / 输入 / 处理 / 输出 / 不做什么），砍功能三把刀；
- 架构：**进、存、取三问** -- 先画「取」再画「进」，只画「东西」不画「工具」，架构分版本；
- 技术：**四原则** -- AI 最熟 / 本地能跑 / 文件优先 / 社区大。

三份 `docs/` 文档 = 这套方法论的完整模板 + 一份真实填写示例，照填一遍就是你自己的版本。

## 边界：本项目和公司级知识库的区别

本项目的适用量级是**个人知识库（几千篇以内）**。按「进、存、取」三层对照，个人版与公司级的差异如下：

| 层 | 本项目（个人级） | 公司级需要 | 升级原因 |
| --- | --- | --- | --- |
| 进 | 手动发指令，AI 会话同步处理 | 连接器 + 消息队列 + 异步 worker；增量同步、去重、多格式解析（PDF / 音视频 / OCR） | 来源从 1 个变 N 个，量从每天几条变几千条 |
| 存 · 原料 | 本地 `raw/` 文件 | 对象存储（S3 / OSS）+ 元数据入 PostgreSQL | 本地文件无法共享、备份容灾、权限控制 |
| 存 · 加工 | AI 当场景总结、写笔记 | 离线流水线：批处理总结 / 打标，模型分级（入库小模型、问答大模型） | token 成本随量级爆炸，必须工程化降本 |
| 存 · 目录 | 单个 `index.md` | 检索系统：ES 关键词 + 向量库（Milvus / pgvector）混合检索 + rerank | 索引会撑爆 AI 上下文 |
| 存 · 编译 | 每入库一篇就重写项目页 | 增量编译 / 定时编译（变更检测驱动） | 每篇全量重写在公司级是 O(n²) 成本 |
| 取 | AI 会话问答 | RAG 服务：检索 → 组装上下文 → 生成 + 引用；Web / IM / API 多端 | 用户从 1 人变万人，不可能人人开会话翻文件 |
| 取 · 权限 | 无（自用） | ACL 继承：检索结果按用户权限过滤 | 绝不能答出提问者无权看的内容 |

一句话：个人版是「AI 即基础设施」，公司级是「AI 变成流水线上的一个环节」。分层存储（原料只读 / 加工编译 / 目录导航）、编译 > 检索、往回织的理念在公司级依然成立，要换的只是每一层的实现载体。本项目刻意停在个人量级：零代码、零依赖。

### 附：「往回织」在十万级还成立吗？

理念成立，机制要换。成本模型是 **O(N × k)**：N 是总笔记数，k 是单个项目页挂载的笔记数。「每入库一篇就全量重写项目页」时，单一主题的处理成本随笔记量平方增长；且 k 到几千后，项目页本身会超出 AI 上下文 -- 不是贵，是织不动了。

所以关键不是总量 N，是单主题堆积 k：**k 有界（主题及时裂变），总成本对 N 就是线性的，十万级可行**。规模化前需要替换的机制：

- **增量织**：不再全量重写，只输出变更段落或追加条目（单次 O(1)）；
- **分层编译**：k 超阈值就裂变 -- 笔记 → 子主题页 → 项目页（MapReduce 式，单次只动一个子页）；
- **窗口批量织 + 定期重整**：攒批触发降低写放大，闲时全量重写纠偏（类似 LSM 的 compaction）。
